# IcFalcon — Focus & Not Focus

## Mission

IcFalcon aims to become the **production framework for building ICP applications with humans and AI agents**.

The goal is not to have the most packages.

The goal is to make serious ICP applications **fast, safe, scalable, and AI-buildable**.

---

# Focus

## 1. Money Core — Highest Priority

Build a production-quality ICP financial foundation.

### Core packages

* `ledger`
* `subaccount`
* `icrc1`
* `icrc2`
* `wallet`
* `transfer`
* `transaction`
* `deposit`

### Requirements

Money packages must be:

* composable
* strongly typed
* reusable
* testable
* production-oriented
* safe for AI-generated code
* minimal in API surface
* documented with real examples

Handle important financial concerns:

* transfer fees
* validation
* authorization
* deduplication
* transaction history
* pagination
* error normalization
* subaccounts
* ICRC compatibility

### Dependency direction

Keep dependencies one-way:

```text
Foundation
    ↓
Money Core
    ↓
Extensions
    ↓
Applications
```

Do not create circular dependencies.

---

# 2. AI-Native Development

`.agents/skills` is a core IcFalcon feature.

AI agents must be able to understand:

* which package to use
* how to use it
* architecture rules
* security requirements
* testing requirements
* deployment requirements
* common ICP pitfalls

Skills should contain actionable implementation knowledge, not only documentation.

Example:

```text
.agents/
└── skills/
    ├── wallet/
    ├── icrc/
    ├── auth/
    ├── payments/
    ├── storage/
    ├── testing/
    └── deployment/
```

The target workflow:

```text
Human request
    ↓
AI agent
    ↓
IcFalcon skills
    ↓
IcFalcon packages
    ↓
Generated application
    ↓
Tests
    ↓
Security checks
    ↓
Deployment
```

---

# 3. CLI

The CLI should make common development tasks extremely simple.

Examples:

```bash
falcon new my-app
falcon m:f Wallet
falcon add wallet
falcon add payments
falcon add storage
falcon dev
falcon test
falcon deploy
```

Prioritize:

* predictable commands
* fast scaffolding
* composability
* generated code quality
* AI compatibility

---

# 4. Production Safety

IcFalcon should help developers avoid common mistakes, especially when code is generated by AI.

Build toward:

```bash
falcon doctor
falcon security
```

Checks should include things such as:

* authorization
* transfer validation
* duplicate transaction protection
* fee handling
* error handling
* missing configuration
* test coverage
* unsafe patterns

The goal:

> AI can generate the application, while IcFalcon helps enforce production standards.

---

# 7. High-Quality Packages Over Package Count

Do not optimize for:

```text
92 packages → 200 packages → 500 packages
```

Optimize for:

```text
fewer
+
deeper
+
better tested
+
better documented
+
more reusable
```

Every package should justify its existence.

Before creating a package ask:

1. Is this a real ICP development problem?
2. Will multiple applications reuse it?
3. Can it have a clean API?
4. Does it reduce complexity?
5. Can an AI agent use it reliably?

If the answer is mostly no, do not create it.

---

# 8. ICP-Native Features

IcFalcon should take advantage of what makes ICP different.

Prioritize primitives around:

* canisters
* Internet Identity
* ICRC
* subaccounts
* stable memory
* inter-canister calls
* HTTP outcalls
* scheduled execution
* on-chain storage
* ckBTC
* application-level payments

Do not blindly copy Ethereum/Solana architecture.

Build for ICP.

# Not Focus

## 1. Package Count

Do not create packages simply to increase the registry count.

Bad:

```text
tiny-helper-1
tiny-helper-2
tiny-helper-3
```

Prefer reusable primitives.

---

## 2. Generic CRUD as the Main Product

CRUD scaffolding is useful infrastructure, but it is not the core identity of IcFalcon.

CRUD should support the framework, not define it.

The main identity is:

```text
ICP
+
Production primitives
+
Money
+
AI development
```

---

## 3. Competing as a Generic Web3 Framework

Do not try to become:

> "Hardhat/Foundry for every blockchain."

IcFalcon should win by being excellent at ICP.

Positioning:

```text
IcFalcon
    ↓
ICP-native
    ↓
AI-native
    ↓
Production applications
```

---

## 4. DeFi Before Money Core

Do not rush into:

* DEX
* swaps
* complex escrow
* advanced DeFi
* liquidity protocols

before:

```text
ledger
subaccount
icrc1
icrc2
wallet
transfer
transaction
deposit
```

are stable.

---

## 5. Complex AI Features Before Reliable Primitives

Do not prioritize autonomous agents, elaborate orchestration, or AI features while the underlying packages are incomplete.

Correct order:

```text
Reliable primitives
        ↓
Good skills
        ↓
AI tooling
        ↓
Autonomous workflows
```

---

## 6. Duplicate Implementations

Avoid duplicated business logic.

Bad:

```text
wallet/transfer.mo
deposit/transfer.mo
payment/transfer.mo
marketplace/transfer.mo
```

with different transfer implementations.

Prefer:

```text
transfer
   ↑
wallet
deposit
payment
marketplace
```

One well-designed primitive should be reused everywhere possible.

---

## 7. Over-Abstraction

Do not create abstractions merely for architectural appearance.

Avoid:

```text
interface
    ↓
manager
    ↓
adapter
    ↓
factory
    ↓
service
    ↓
repository
```

when a simpler design is sufficient.

Every abstraction must provide real value.

---

## 8. Premature Enterprise Features

Do not prioritize features such as:

* complex multi-cloud deployment
* Kubernetes orchestration
* enterprise dashboards
* unnecessary microservices
* complicated plugin systems

until the core ICP developer experience is excellent.

---

# Decision Rule

Before implementing a feature, classify it.

### Build now

If it improves:

```text
ICP development
+
Money
+
AI development
+
Security
+
Developer experience
```

### Consider later

If it improves:

```text
advanced integrations
advanced DeFi
enterprise features
additional ecosystems
```

### Reject or defer

If it mainly:

```text
increases package count
adds abstraction without value
duplicates existing functionality
copies another ecosystem
does not solve an ICP problem
```

# Final Principle

IcFalcon should not try to be the framework with the most features.

It should become:

> **The fastest, safest, and most AI-friendly way to build production applications on the Internet Computer.**

When choosing between **more features** and **better core infrastructure**, choose the better core infrastructure.
